## Deployed Render Free service

[Render supports full Next.js as a Node web service](https://render.com/docs/deploy-nextjs-app). The manually created service `keyline-rental-inventory` (`srv-db54cj2vcj2c738dnak0`) is Free, uses Singapore and the migration branch, and serves [https://keyline-rental-inventory.onrender.com](https://keyline-rental-inventory.onrender.com). Its first successful deploy is `dep-db54cjivcj2c738dnb50`, sourced from commit `11ba8ee`. The first environment-update build `dep-db5503dckfvc73901240` succeeded, but upload configuration checks returned HTTP 503 because the saved private-key setting was still blank. The approved key was then filled and privately checked in the editable field before saving. Rebuild `dep-db552c7lk1mc738p8f2g` is now live after 1 minute 59 seconds; the Node server reported ready in 1,793 ms. A real authorized 8,355,073-byte owner upload returned HTTP 200 in 3,584 ms with exactly `id`, `path`, `name`, `url` and `createdAt`, validating the runtime credential. Firebase Auth authorizes the actual Render hostname with earlier domains preserved.

The Render public scan after the corrected credential deployment inspected 29 HTML/JavaScript resources totaling 1,491,982 bytes and found no raw or Basic-encoded ImageKit private key. The combined public-resource SHA-256 is `103f05b07dfc07c1e3f2cea9fafd65dca6c98a720c7e976d78a6959b16d3947a`.

`render.yaml` records the target final configuration: `plan: free`, Singapore, Node 24.19.0, pinned pnpm 11.25.0, a normal Next build, port `$PORT` on `0.0.0.0`, and `/login` health checking. Its `branch: main` is the intended release setting; the actual service still uses the migration branch until main is pushed. This service was created manually and is not automatically linked to the file as a Render Blueprint. The file contains unset environment placeholders and provisions no database, disk, worker or paid add-on. The existing unrelated service remains untouched.

The authenticated workspace shows Hobby, no card on file and $0 accrued/projected charges. [Without a payment method, Render suspends Free services or builds when included usage is exhausted](https://render.com/docs/free); adding a card would introduce automatic bandwidth/build overage charges even on Free instances. Keep it absent. This workspace shares 750 Free hours, 5 GB outbound bandwidth and 500 pipeline minutes monthly with its existing service. The Free service has 512 MB RAM/0.15 CPU. CPU/memory graphs require an upgrade and were not enabled, so no exact resource-usage measurement is claimed. The displayed outbound usage was 2 MB at the checkpoint and updates with an hourly lag.

[Render Free sleeps after 15 idle minutes and can take about a minute to resume](https://render.com/docs/free). Local filesystem changes disappear on restart; application records/images already persist in Firestore/ImageKit. Render discourages Free use for production and can suspend unusually high outbound API/storage traffic. The requested low-traffic no-card deployment retains those availability limitations despite passing migration verification.

## Secrets and public build settings

| Setting                              | Local development                                 | Render service                                                         |
| ------------------------------------ | ------------------------------------------------- | ---------------------------------------------------------------------- |
| `NEXT_PUBLIC_FIREBASE_*`             | Public `.env.local` values                        | Public service environment values compiled for production Firebase     |
| `NEXT_PUBLIC_USE_FIREBASE_EMULATORS` | `true` only for local demo Auth/Firestore         | `false`                                                                |
| `IMAGEKIT_PRIVATE_KEY`               | Ignored `.dev.vars`, loaded by Node 24 `pnpm dev` | Approved private service environment setting, used only by server code |
| `IMAGEKIT_URL_ENDPOINT`              | Ignored `.dev.vars`                               | Service environment setting for the server upload handler              |

Copy blank `.dev.vars.example` into `.dev.vars` and fill it locally. On Render, the existing approved ImageKit settings are saved only in the private service environment, with no credential values in tracked configuration, documentation, screenshots or logs. The normal Next.js Node build can receive server environment values during build and runtime. The private key has no `NEXT_PUBLIC_` prefix and stays behind the `server-only` upload module; it is never a browser setting. The Node deployment does not invoke OpenNext or its environment-file serializer. Inspect the actual deployed public HTML/JavaScript before accepting the host. The proxy needs no Firebase admin/service-account credentials.

For **OpenNext/Cloudflare builds specifically**, keep both ImageKit variables out of every `.env*` file and private keys out of the build process. The installed adapter serializes environment files into `cloudflare/next-env.mjs`, including values without a public prefix; runtime overrides do not remove an embedded copy. The Cloudflare preflight rejects a nonempty private key in `.env*` or the build process. That deployment uses runtime secrets only. [OpenNext compiler](https://github.com/opennextjs/opennextjs-cloudflare/blob/main/packages/cloudflare/src/cli/build/open-next/compile-env-files.ts), [Local secrets](https://developers.cloudflare.com/workers/local-development/environment-variables/).

The historical custom Worker also needs the intentionally public `NEXT_PUBLIC_FIREBASE_API_KEY` and `NEXT_PUBLIC_FIREBASE_PROJECT_ID` at runtime because its direct TypeScript handler bypasses Next's public-value compiler. Those values and both ImageKit settings are already configured there; `--keep-vars` preserves them. Do not add the private key to Workers Builds variables/secrets. Future Cloudflare rotations use interactive `wrangler secret put` prompts, never command-line values.

## Upload authorization and retention

`POST /api/photos` receives the user's Firebase token and one image. Firebase Auth REST validates the account; Firestore REST reads profile/property/tenancy under that token, preserving Security Rules. Landlords must own an unarchived property. Tenants require a verified matching email and an Active, unarchived tenancy.

The server bounds the body at 8 MiB, accepts JPEG/PNG/WebP, checks signatures against MIME type, generates the UID-scoped path, and privately authenticates to ImageKit. New metadata retains the frozen `{id, url, path, name, createdAt}` format. ImageKit's file ID is validated on the server and is not persisted for new uploads. Earlier verification photos with paired `provider: "imagekit"` and `fileId` remain strictly compatible. The historical custom Cloudflare entry calls this same handler before Next's request conversion; only Wrangler aliases the `server-only` marker, while Next application builds retain their client boundary enforcement. No authorization bypass is introduced.

Local integration against live Firebase/ImageKit passed real owner and verified-tenant uploads, mixed two/ten-photo records, immutable check-in/check-out, tenant confirmation, report evidence, repair notes and completed-tenancy access revocation. All 37 live security/retention checks passed. Later public Cloudflare verification passed these workflows again, plus 24 fixture isolation/retention checks and 14 retained-history/upload checks. Production rules match the local source and two indexes are ready.

On Render, the owner saved/reloaded fresh item photos and a property-description edit. The verified tenant saved/reloaded a new report with real 720-pixel evidence; the owner saved Repairing and a note visible to the tenant. Completing the tenancy again clears tenant inventory and disables new reporting/uploads while retaining both snapshots, reports, notes and original photos. Comparison still shows Good/two photos versus Damaged/one, with all three images and changes-only filtering passing. The unverified tenant remains gated, and the generic password-reset request passes.

Security/history/evidence checks pass in both Active and Completed states, including unrelated-account denial, MIME spoof 400, real 8 MiB + 1 byte 413, canonical five-field metadata and exact retained image bytes. Mobile report/history/comparison at 390 × 844 has 375-pixel scroll width; the add-item form fits 390 pixels with enabled multiple-photo/camera controls. The existing Cloudflare fixture is reused: owner registration and handover creation/confirmation were verified there rather than repeated on Render. The generic Render password-reset request passed; reset-link delivery/action and email actions after the Render deployment were not rechecked. Actual device camera capture remains unverified. Public resources, available runtime logs, repository candidates, built client files and all branch-history patches were scanned privately for raw/Basic-encoded private-key matches and found none.
