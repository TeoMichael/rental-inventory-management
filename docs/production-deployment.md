## Secrets and public build settings

| Setting                              | Local development                                 | Render service                                                         |
| ------------------------------------ | ------------------------------------------------- | ---------------------------------------------------------------------- |
| `NEXT_PUBLIC_FIREBASE_*`             | Public `.env.local` values                        | Public service environment values compiled for production Firebase     |
| `NEXT_PUBLIC_USE_FIREBASE_EMULATORS` | `true` only for local demo Auth/Firestore         | `false`                                                                |
| `IMAGEKIT_PRIVATE_KEY`               | Ignored `.dev.vars`, loaded by Node 24 `pnpm dev` | Approved private service environment setting, used only by server code |
| `IMAGEKIT_URL_ENDPOINT`              | Ignored `.dev.vars`                               | Service environment setting for the server upload handler              |

Copy blank `.dev.vars.example` into `.dev.vars` and fill it locally. On Render, the existing approved ImageKit settings are saved only in the private service environment, with no credential values in tracked configuration, documentation, screenshots or logs. The normal Next.js Node build can receive server environment values during build and runtime. The private key has no `NEXT_PUBLIC_` prefix and stays behind the `server-only` upload module; it is never a browser setting. The Node deployment does not invoke OpenNext or its environment-file serializer. Inspect the actual deployed public HTML/JavaScript before accepting the host. The proxy needs no Firebase admin/service-account credentials.

For **OpenNext/Cloudflare builds specifically**, keep both ImageKit variables out of every `.env*` file and private keys out of the build process. The installed adapter serializes environment files into `cloudflare/next-env.mjs`, including values without a public prefix; runtime overrides do not remove an embedded copy. The Cloudflare preflight rejects a nonempty private key in `.env*` or the build process. That deployment uses runtime secrets only. [OpenNext compiler](https://github.com/opennextjs/opennextjs-cloudflare/blob/main/packages/cloudflare/src/cli/build/open-next/compile-env-files.ts), [Local secrets](https://developers.cloudflare.com/workers/local-development/environment-variables/).

The historical custom Worker also needs the intentionally public `NEXT_PUBLIC_FIREBASE_API_KEY` and `NEXT_PUBLIC_FIREBASE_PROJECT_ID` at runtime because its direct TypeScript handler bypasses Next's public-value compiler. Those values and both ImageKit settings are already configured there; `--keep-vars` preserves them. Do not add the private key to Workers Builds variables/secrets. Future Cloudflare rotations use interactive `wrangler secret put` prompts, never command-line values.

## Upload authorization and retention

`POST /api/photos` receives the user's Firebase token and one image. Firebase Auth REST validates the account; Firestore REST reads profile/property/tenancy under that token, preserving Security Rules. Landlords must own an unarchived property. Tenants require a verified matching email and an Active, unarchived tenancy.

The server bounds the body at 8 MiB, accepts JPEG/PNG/WebP, checks signatures against MIME type, generates the UID-scoped path, and privately authenticates to ImageKit. New metadata retains the frozen `{id, url, path, name, createdAt}` format. ImageKit's file ID is validated on the server and is not persisted for new uploads. Earlier verification photos with paired `provider: "imagekit"` and `fileId` remain strictly compatible. The historical custom Cloudflare entry calls this same handler before Next's request conversion; only Wrangler aliases the `server-only` marker, while Next application builds retain their client boundary enforcement. No authorization bypass is introduced.

Local integration against live Firebase/ImageKit passed real owner and verified-tenant uploads, mixed two/ten-photo records, immutable check-in/check-out, tenant confirmation, report evidence, repair notes and completed-tenancy access revocation. All 37 live security/retention checks passed. Later public Cloudflare verification passed these workflows again, plus 24 fixture isolation/retention checks and 14 retained-history/upload checks.
